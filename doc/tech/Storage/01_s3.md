# S3 Storage

## Buckets description

The stack requires several S3 buckets.

 - phrasea-databox
   - Stores databox files and renditions referenced by assets.
   - Can be exposed through a CDN.
   - Is private, and access is performed through signed URLs.

 - phrasea-statics
   - Stores static files used by Phrasea modules, including:
     - Databox, Expose, and Uploader MUI themes.
     - Logos used on Keycloak login pages.
     - Interface design customization files and rendition watermark files.
   - Requires public access.
   - Setting CORS rules to limit allowed origins is recommended.
 
 - phrasea-uploader
   - Stores files uploaded through Phrasea Uploader.
   - Is private, and access is performed through signed URLs.

 - phrasea-expose
   - Stores files used by the Phrasea Expose module.
   - Can be exposed through a CDN.
   - Is private, and access is performed through signed URLs.

Bucket naming is flexible, but bucket names must be reported in the stack configuration.
See [environment configuration variables](../Configuration/env_var), especially the [S3-Compatible Storage Settings](../Configuration/env_var#s3-compatible-storage-settings) section.

With the bundled MinIO, each consumer can get a user restricted to its bucket instead of the root keys: see [MinIO users](../01_setup.md#minio-users).

## S3 Addressing Style

The S3 client addressing style must match your object storage provider behavior.

- `S3_USE_PATH_STYLE_ENDPOINT=true` means path-style addressing (bucket name after the endpoint domain).
- `S3_USE_PATH_STYLE_ENDPOINT=false` means virtual-hosted-style addressing (bucket name as a subdomain).

For the environment variable reference, see [Environment Variables](../Configuration/env_var#s3-compatible-storage-settings).


In Helm deployment values, the equivalent setting is `usePathStyleEndpoint`.

## Multipart Upload Settings

Phrasea uploads large files using S3 multipart upload.

The **API decides the part size**: when a client creates an upload (`POST /uploads` with the file size), the API computes the smallest part size (at least `S3_MULTIPART_MIN_CHUNK_SIZE`) that fits the file in `S3_MULTIPART_MAX_PART_NUMBER` parts, creates the S3 multipart upload and answers with `chunkSize` and the presigned `PUT` URLs of the **first 1 000 parts** (`urls`, keyed by part number). Clients then upload the parts directly to the storage, several in parallel, without asking the API for each URL.

Part URLs are valid for 3 hours. `POST /uploads/{id}/parts` (body `{"from": <part number>}`) returns fresh URLs from that part, 1 000 at most, together with `chunkSize` and `partCount`; clients use it to resume an interrupted upload, after a URL expired during a long transfer and to get the URLs past the first 1 000 parts. The part size is persisted with the upload so a resumed upload keeps the same slicing even if these limits are reconfigured in between.

An upload belongs to the user (or OAuth client) who created it: only this owner (or an admin) can read it, get its part URLs or cancel it, and only the owner can complete it into a resource (asset, rendition, logo...). An upload is used once: the request completing it reserves it atomically before reaching S3 (concurrent requests get a 400 "already used"), so that two resources never share the same S3 object; if S3 refuses the completion, the reservation is released and the client can retry. On completion, the API checks the size of the object stored on S3: if it differs from the declared size or exceeds the maximum file size of the application, the object and the upload are deleted and the request is refused.

### Upload limits

Every multipart upload opens an upload on S3 and signs part URLs, so the APIs limit them **before** anything is created on the storage:

- **Maximum file size**, per application, within `S3_MAX_OBJECT_SIZE`: `DATABOX_MAX_UPLOAD_FILE_SIZE` and `EXPOSE_MAX_UPLOAD_FILE_SIZE` (default 100 GiB), the stack configuration `uploader.max_upload_file_size` for the uploader (`alchemy_storage.upload.max_file_size` in the Symfony configuration). A larger declared size is refused when the upload is created (400), a larger stored object when it is completed. The parts are sent straight to S3 with presigned URLs, which cannot bind their length: the size of what was really stored is only known on completion.
- **Rate limit**, per user: `MULTIPART_UPLOAD_RATE_LIMIT` requests per minute (default 60, sliding window) to create an upload or get part URLs (`POST /uploads`, `POST /uploads/{id}/parts`). Beyond, the API answers 429 with a `Retry-After` header; both client implementations wait for that delay and send the request again. The limiter (`alchemy_storage_multipart_upload` in `framework.rate_limiter`) stores its state in the `cache.rate_limiter` pool unless the application sets its own `cache_pool` (one shared by its replicas).
- **Uploads in progress**, per user: at most `MULTIPART_UPLOAD_MAX_PENDING` (default 20) uploads created in the last 24 hours and neither completed nor cancelled; beyond, the creation answers 429 (without `Retry-After`: complete or cancel some uploads first).

The holders of an uploader upload link share these limits, whatever their browser session. Through a link, the creation is also refused (400 `upload_link_quota_exceeded`) when the link is exhausted or when the declared size exceeds what remains of its total size; the file is counted against the link when the upload is completed. The `AssetToken` of a commit cannot use `/uploads` (403).

Every client goes through one of two shared implementations of this protocol: the JS engine exported by `@alchemy/api` (`lib/js/api/src/multiPartUpload.ts`, transport-agnostic, used by the databox and uploader clients; axios clients go through `src/axiosMultipartUpload.ts`) and, for server-to-server pushes (e.g. databox publishing to expose), the PHP service `Alchemy\CoreBundle\Upload\MultipartUploader`.

Depending on your filer or object storage provider, you may need to adjust multipart limits to match platform capabilities. These variables are read by the API containers (databox, expose, uploader):

- `S3_MULTIPART_MIN_CHUNK_SIZE` (default 5 MiB, the S3 minimum)
- `S3_MULTIPART_MAX_CHUNK_SIZE` (default 5 GiB)
- `S3_MULTIPART_MAX_PART_NUMBER` (default 10 000)
- `S3_MAX_OBJECT_SIZE` (default 5 TiB, the largest object of S3; also read by the clients to reject oversized files before uploading)

If these values do not match your storage limits, uploads can fail for large files.

For variable definitions, see [Environment Variables](../Configuration/env_var#s3-compatible-storage-settings).


## Bucket CORS Configuration

If a bucket is accessed through cross-origin XMLHttpRequest calls, you must enable CORS for that bucket.

CORS Example :

```json
{
  "CORSRules": [
    {
      "AllowedHeaders": ["*"],
      "AllowedMethods": ["GET", "HEAD", "PUT", "POST", "DELETE"],
      "AllowedOrigins": ["https://*.mydomain.com"],
      "ExposeHeaders": ["ETag", "x-amz-version-id"],
      "MaxAgeSeconds": 3000
    }
  ]
}
```
