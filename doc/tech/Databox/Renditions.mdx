# Renditions

The Rendition Factory is a service responsible for generating various renditions (alternative formats or versions) of media assets stored in Databox. It utilizes a set of transformers to process and convert the original media files into different renditions based on predefined configurations.

## Formats read by ImageMagick

Image renditions (`imagine`, `pdf_to_image`, the colorspace analyzer...) read
the source through ImageMagick, which picks its coder from the first bytes of
the file, whatever its extension or declared type. Uploaded files are not
trusted, so the databox API and worker images restrict ImageMagick to an allow
list (`databox/api/docker/entrypoint.d/01-imagick.sh`, applied when the
container starts):

- **Read and written:** JPEG, PNG, GIF, WEBP, TIFF, HEIC/HEIF/AVIF, PSD, BMP,
  ICO, and PDF (read through the Ghostscript library). An Illustrator file
  saved with PDF compatibility (the default) is read as a PDF.
- **Refused, whatever the extension:** every other coder, in particular
  PostScript and EPS, XPS, SVG, MVG, MSL, text and label pseudo-formats, and
  URLs (`http:`, `https:`, `ftp:`, `url:`). The `@file` syntax (a file holding
  a list of files) is refused as well, and no external delegate program is
  run.

Consequences:

- An SVG file is stored and downloadable, and the `imagine` module still
  passes it through unchanged, but ImageMagick no longer rasterizes it: no
  bitmap rendition is built from an SVG.
- An EPS or PostScript file, and an Illustrator file without PDF
  compatibility, no longer gets a thumbnail.
- Other formats ImageMagick could read before (JPEG 2000, JPEG XL, OpenEXR,
  TGA, XCF...) no longer get a rendition either. To read one of them again,
  add its module to the allow list of `01-imagick.sh` and rebuild the image,
  after weighing the risk: a crafted file can read local files or reach the
  network through some coders.

With the `imagine` module, a refused source fails as an unsupported source
file: the rendition is given up instead of being retried.

## Protocols opened by ffmpeg

Video and audio renditions, and the clips of the exports and of the Expose
publications, run ffmpeg and ffprobe with `-protocol_whitelist file,pipe` on
every input: a source which references other resources (HLS playlist, URL...)
can only make them open local files, never the network
(`RestrictedProcessBuilderFactory`, installed by `FFMpegHelper`).

## Documents converted by LibreOffice (`document_to_pdf`)

The `document_to_pdf` module converts office documents to PDF with LibreOffice.
A rendition definition can be edited by any workspace editor and aim this module
at any file, so the format is told from the **content** of the file, never from
its name or its declared type:

- **Converted:** Word (`doc`, `docx`), Excel (`xls`, `xlsx`), PowerPoint (`ppt`,
  `pptx`), OpenDocument (`odt`, `ods`, `odp`), RTF and plain text. OOXML and
  OpenDocument files are told apart by the `[Content_Types].xml` or `mimetype`
  entry of their archive; the legacy `doc`/`xls`/`ppt` by the content of their
  OLE container. LibreOffice is given the matching import filter and never
  guesses the format: a plain text file is read as text, even if it looks like
  HTML.
- **Passed through:** a PDF (`%PDF-` header), whatever its declared type.
- **Refused, as an unsupported source** (the rendition is given up instead of
  being retried): everything else — HTML, flat XML OpenDocument (`fodt`,
  `fods`…), SVG, images, macro-enabled or template Office files (`docm`,
  `xlsm`, `dotx`…), unknown binaries.

```yaml
document:
    transformations:
        - module: document_to_pdf
          # 300 seconds by default, 1800 at most
          options: {timeout: 600}
```

Each conversion is isolated within the worker process:

- a new LibreOffice profile, copied from
  `lib/php/rendition-factory/src/Transformer/Document/Libreoffice/profile/`
  and deleted afterwards: macros disabled, links to other documents never
  updated, every HTTP, HTTPS and FTP access sent to a proxy on a closed port of
  the loopback (linked images or documents are never fetched);
- an empty environment (no credential of the worker reaches LibreOffice), a
  working directory of its own, the source copied under the name of its
  detected format;
- a timeout (`timeout` option), after which the whole process group is killed,
  `soffice.bin` included.

Not done: there is no kernel sandbox. LibreOffice runs with the user, the
filesystem and the network namespace of the worker; a vulnerability in one of
its import filters would give access to them. Moving the conversion to a
dedicated container without network nor secrets is left as an infrastructure
option.

## Story contact sheet (`generate:`)

A story has no source file of its own until a cover is set. A `generate:` build
definition produces a rendition without any source: its first module is a
generator, fed with the renditions already built for the story items. The
`contact_sheet` generator assembles them in a square grid (2×2 or 4×4).

```yaml
generate:
    # The rendition of the items to assemble: thumbnail (default) or preview
    input: thumbnail
    transformations:
        - module: contact_sheet
          options: {grid: 2, size: 400, gap: 2, format: webp}
```

- The definition must be in `Custom` build mode, without parent, with the `Story` target.
- The items are taken in their story order: not deleted, accepted (not in
  quarantine), whatever the rights of the viewer — the sheet is shown to every
  reader of the story, like a cover. Only their image renditions with a public
  rendition policy are used; an item which never gets one leaves its cell empty.
  An item which is a story brings its own cover or contact sheet.
- The sources of the items are never read. While an item has a source but not
  its rendition yet, the build waits (retried every 30 seconds, 10 times at most,
  then built with the ready items).
- The sheet is rebuilt a few seconds after the story changes: an item added,
  removed or moved, its thumbnail or preview replaced, deleted, restored, or
  accepted out of quarantine. An unchanged list of inputs keeps the existing file.
- The new workspaces have a `StoryContactSheet` definition (2×2, used as
  thumbnail and animated thumbnail). For an existing workspace, create it in
  the rendition definitions tab with the definition above. For a 4×4 grid, set
  `grid: 4`; create two definitions to get both.

A story with a cover takes its thumbnail from the cover and shows the contact
sheet on hover (the animated thumbnail); a story without cover shows the sheet
in both cases. In the list, moving the pointer horizontally over the sheet
then shows the carousel of the items.
